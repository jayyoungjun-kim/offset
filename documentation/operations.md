# OFFSET 운영 및 연결 가이드

2026-09-07 · v0.1

현재 QA 운영 기준은 [DEPLOYMENT.md](../DEPLOYMENT.md)를 따른다. 리뉴얼은 https://qa.offset.quest 에서 검증하고 offset.quest 운영 화면은 유지한다. 아래 초기 구축 설명 중 원격 연결 전 상태는 첫 로컬 구현 당시의 기록이다.

## 현재 완료 범위

- `/programs`: 검색·유형·상태 필터가 있는 반응형 리스트.
- `/programs/portfolio-workshop`: 실제 초기 워크숍 상세. 모집 마감 상태.
- `/login`: Google OAuth 진입 및 설정 미완료/실패 상태.
- `/account`: 로그인 회원 본인의 신청·검토 상태.
- `/admin`: 운영자 권한이 있는 계정만 데이터 조회·저장.
- `/admin/preview`: 공개 초기 데이터만 사용하는 읽기 전용 운영 UI 미리보기. 프로그램 편집 폼을 볼 수 있지만 저장 불가.
- `/apply`: 새 상세로 이동. `/api/applications` POST는 로그인과 중복 제한을 적용하는 새 신청 API의 호환 별칭. 기존 파일 업로드는 종료하고 링크로 신청.
- 기존 홈·About·워크숍 본문과 사용자의 기존 변경을 유지. 헤더의 프로그램 탐색 경로만 새 리스트로 연결.

## 로컬 실행

Node 22.13 이상(테스트의 TypeScript 데이터 import에는 최신 Node 22 또는 Node 24 권장). 이 작업에서 Node 24.19와 pnpm을 사용했다.

```sh
pnpm install --frozen-lockfile
pnpm db:local
pnpm dev
```

`pnpm db:local`은 schema와 초기 프로그램의 마이그레이션을 적용한다. 초기 데이터는 `INSERT OR IGNORE`로 저장되어 운영자가 수정한 내용은 덮어쓰지 않는다. `.wrangler`는 로컬 DB와 임시 검증 파일이며 Git에서 제외된다. `wrangler.local.json`은 로컬 전용이며 운영 배포에 사용하지 않는다.

```sh
pnpm typecheck
pnpm build
pnpm test:platform
```

통합 테스트는 별도 로컬 데이터베이스와 포트 3011을 사용한다. 가상의 테스트 회원과 세션은 이 DB에만 주입하며 Google 인증을 대체하는 앱 기능은 없다. 테스트 종료 시 해당 DB를 삭제한다. 실제 Google 계정 로그인 왕복 검증은 별도다.

## Google 연결

1. Google Cloud의 OAuth 웹 애플리케이션을 선택/생성하고 동의 화면의 브랜드·지원 이메일·테스트 사용자를 설정한다.
2. 로그인할 정확한 출처를 정한다. 로컬 예시는 `http://localhost:3000`, 운영은 Worker로 연결한 실제 도메인이다.
3. 승인된 리디렉션 URI에 `http://localhost:3000/api/auth/callback`을 등록한다. QA와 운영 주소도 각각 정확히 등록한다.
4. `.env.example`을 참고해 `.env.local`과 호스팅 비밀 환경 변수에 아래 값을 입력한다. 기존 `.env.local`을 덮어쓰지 않는다.

```dotenv
GOOGLE_CLIENT_ID=발급된 값
GOOGLE_CLIENT_SECRET=발급된 비밀 값
AUTH_ORIGIN=http://localhost:3000
ADMIN_EMAILS=실제로 사용할 운영자 Google 이메일
```

비밀키를 저장소·문서·채팅에 넣지 않는다. 관리자 메일은 쉼표로 구분한다. 설정 변경 후 개발 서버를 재시작한다. 운영자 허용 목록에서 이메일을 제거하면 이후 요청부터 운영 API 접근이 차단된다.

실제 구글 인증 연결 정보는 제공되지 않았으므로 현재는 준비 상태다. 버튼만 활성화하거나 임의 로그인 세션을 만들어 완료된 것으로 취급하지 않는다.

## 프로그램 운영

1. 운영자로 로그인하고 어드민에서 프로그램을 만든다. 최초 상태는 초안을 권장한다.
2. 제목, slug, 유형, 일정, 비용, 대상·학습 결과·진행 과정, 멘토를 실제 운영 내용으로 확인한다.
3. 이미지는 `public`의 이미지 경로를 사용한다. 초기 버전에는 파일 업로드 UI가 없다.
4. 공개하려면 모집 중 또는 모집 마감으로 저장한다. 초안은 목록과 직접 URL에서 숨겨진다.
5. 마감한 프로그램은 상세와 카드에서 상태가 표시되고 API도 접수를 막는다. 정원은 운영 안내이며 자동 정원 제한·결제 예약 기능은 아직 없다.
6. 목록의 표시 순서를 낮은 숫자부터 관리한다. 기존 신청이 있는 프로그램은 id를 유지한다. 영구 삭제 대신 초안 상태로 숨긴다.

## 신청과 개인정보

- 신청은 포트폴리오 링크, 20자 이상의 동기, 개인정보 수집 동의가 필요하다. 회원 이름과 이메일은 서버의 로그인 정보에서 가져온다.
- 회원별 동일 프로그램 신청은 1건으로 제한한다. 취소 이후 재신청 기능은 별도 정책 결정 전까지 제공하지 않는다.
- 운영자의 상태 변경은 마이페이지에 반영되지만 이메일·문자를 자동 발송하지 않는다.
- 참가 가능은 결제 완료·수강 확정을 의미하지 않는다. 결제 시스템과 실제 강의 콘텐츠 제공은 다음 범위다.
- 초기 폼에는 신청일 기준 1년 보관을 제안했다. 운영 정책 확정 전 실제 개인정보를 접수하지 않는다. 보관 기간에 맞춘 정기 삭제와 회원 탈퇴 처리는 운영 출시 전에 연결해야 한다.
- 프로그램 및 신청 상태 변경은 `audit_log`에 행위자, 작업, 대상과 시각만 기록하며 포트폴리오·동기 전문은 기록하지 않는다.
- 로그인·계정·어드민에서는 기존 상담 위젯을 로드하지 않는다.

## 배포

현재 `.openai/hosting.json`의 기존 프로젝트 id를 유지하고 D1 논리 바인딩 `DB`를 선언했다. 이후 사용자 요청에 따라 해당 QA 프로젝트에 D1 마이그레이션과 QA 전용 환경 설정을 적용해 배포했다. 운영 도메인의 공개 사이트는 변경하지 않았다.

기존 GitHub Pages는 정적 호스팅이다. 이번 기능을 운영하려면 Workers 서버에 배포해야 한다. `dist/server/index.js`, `dist/client`, D1 스키마와 초기 데이터 마이그레이션을 포함한다. 기존 `scripts/build-github-pages.mjs`는 플랫폼 기능을 배포할 수 없으므로 D1 사용 시 실행을 차단한다.

QA 순서: 별도 DB → 마이그레이션 → 비밀 변수 → Worker 배포 → Google 로그인 왕복 → 운영자/일반 회원 권한 및 모바일 검증 → 운영 도메인 전환. 기존 QA 우선 정책과 사용자 변경을 유지한다. QA 검증 이전 main 병합과 운영 교체는 하지 않는다.

## 추가 확인 항목

- 실제 Google Cloud 프로젝트와 운영자 이메일, 콜백 도메인.
- 신청 폼의 개인정보 고지, 보관 기간, 회원 탈퇴·삭제 흐름.
- 실제 모집 일정·정원과 가격, 결제·취소·환불 조건.
- 데스크탑/모바일 실제 브라우저에서 시각, 키보드, 스크린리더 검증.
- 운영 모니터링, DB 백업과 복구, 이메일 알림, 자동 정원 처리.
