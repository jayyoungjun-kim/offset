# OFFSET / Service Blueprint
2026.09.07 · Version 0.4 · 전략, 디자인, 개발의 공통 기준

OFFSET을 단일 워크숍 소개 사이트에서 지속적으로 운영할 수 있는 디자인 러닝 플랫폼으로 확장한다. 첫 구축 범위는 프로그램 리스트, 상세, 구글 로그인, 신청 관리, 확장 가능한 운영 콘솔이다.

핵심은 강좌 수를 늘리는 것이 아니라, 검증된 배움이 반복되는 구조를 만드는 것이다. 실제 상품, 명확한 참여 조건, 신뢰할 수 있는 신청 내역을 먼저 갖춘다.

현재 서비스에 대한 사실과 새롭게 제안하는 운영 방향을 구분한다. 이 문서는 확정된 사업계획이나 성과 보고서가 아니라, 현재 서비스와 저장소를 토대로 작성한 초기 제품 설계 문서다.

현재 공개 가능한 프로그램은 포트폴리오 워크숍 1개다. 저장소의 최신 내용에 맞춰 1기 모집 마감, 9명, 그룹당 3명으로 반영했다. 신규 프로그램, 일정, 수강 후기, 매출과 성과 수치는 임의로 만들지 않았다.

# 01 / 서비스의 현재와 다음 단계
## 확인한 현재 서비스
Offset 홈페이지는 디자이너가 배우고 성장하는 방식을 탐구하는 디자인 러닝 플랫폼이라고 소개한다. About 원고는 지속적인 배움, 반복적인 개선, 관점의 공유, 앞으로의 이동이라는 네 가지 원칙을 제시한다.

현재 대표 프로그램은 기존 포트폴리오를 가진 주니어 프로덕트 디자이너를 위한 소규모 오프라인 워크숍이다. 현업과 채용의 관점에서 리뷰와 수정을 반복하는 경험을 제공한다. 처음부터 포트폴리오를 만드는 과정이나 취업 보장 서비스가 아니다.

## 제품 관점의 해석
Offset의 차별점은 지식의 양보다 작업에 반영되는 피드백의 밀도에 있다. 핵심 고객은 포트폴리오를 가지고 있지만 다음 개선 방향을 결정하기 어려운 디자이너다. 프로그램 탐색부터 참여 이후까지 개선의 흐름이 이어져야 한다.

## 우선 해결할 문제
현재 정적 사이트는 안내 중심이다. 프로그램이 늘 때 목록과 상세가 흩어지고, 신청과 회원 식별이 별개로 관리되기 쉽다. 동일한 프로그램 데이터와 서버의 회원 식별을 사용해 운영자의 반복 작업과 상태 불일치를 줄인다.

# 02 / 제품 구조와 사용자 여정
## 탐색에서 참여까지
프로그램 목록 → 상세 조건 확인 → Google 로그인 → 신청서 제출 → 신청 내역 확인 → 운영자 검토 → 참가 안내. 신청 제출은 결제나 참가 확정을 의미하지 않는다.

## 리스트
프로그램 수와 정렬만 상단에 제공한다. 카드는 대표 이미지, 제목, 진행 방식, 유형과 기수, 모집 상태 순서다. 최신순·모집 중 우선·낮은 가격순으로 정렬하며 공개 프로그램이 하나여도 실제 데이터만 노출한다.

## 상세
기존 워크숍 원문의 소개, 참여 대상, 진행 과정, 멘토, 워크샵 정보, 신청 절차, FAQ를 그대로 보존한다. 데스크탑은 오른쪽 신청 패널, 모바일은 하단 신청 버튼을 사용한다. 모집 마감은 버튼과 서버 양쪽에서 적용한다.

## 계정과 신청
로그인하지 않아도 정보를 읽을 수 있다. 신청은 로그인한 계정에 연결하고 중복 신청을 막는다. 마이페이지에는 해당 회원의 신청만 표시한다. 결제 시스템과 온라인 강의 재생은 이번 단계의 범위가 아니다.

# 03 / 디자인 방향
## 미니멀한 프로그램 인덱스
Pretendard 가변 폰트를 로컬 제공하고 OFFSET 로고를 재사용한다. 흰 바탕과 잉크색 텍스트, 가는 구분선으로 정보의 관계를 정리하고, 블랙을 주요 행동과 중요한 상태에 사용한다. 여백, 숫자, 타이포그래피가 시각적인 인상을 만든다.

## 원티드에서 취한 원칙
참고 리스트는 필터 이후 바로 결과가 나오고 카드 정보가 반복되는 구조다. 참고 상세는 핵심 정보와 신청 행동을 분리해 읽기와 결정을 지원한다. 사용자 지정 Global_guidebook 이벤트 화면의 왼쪽 대표 이미지·본문과 오른쪽 제목·등록·운영자 카드 구조를 따른다. 본문과 이미지에는 OFFSET 원문과 브랜드 자산을 사용한다.

## 데스크탑과 모바일
리스트는 데스크탑 2열, 모바일 1열이다. 상세는 넓은 화면에서 본문과 신청 패널을 나누고, 좁은 화면에서 하나의 읽기 흐름으로 합친다. 어드민 표는 모바일에서 가로 스크롤하고 폼은 한 열로 바뀐다.

## 접근성과 상태
본문 16px 이상, 조작 영역 44px 이상, 명시적인 입력 라벨, 키보드 포커스와 네이티브 대화상자를 사용한다. 로딩, 빈 결과, 오류, 신청 성공과 로그인 준비 상태를 구분한다. 실제 브라우저의 기기별 시각·키보드 검증은 별도 QA 항목으로 남긴다.

# 04 / 운영 콘솔과 확장 모델
## 프로그램이 단일 원본
프로그램 기본 정보, 기수, 유형, 진행 방식, 모집 상태, 순서, 비용, 이미지 경로, 소개, 대상, 진행 과정과 멘토 정보를 관리한다. 저장하면 목록과 상세가 같은 데이터를 사용한다. 초안은 공개 목록과 직접 상세 접근에서 숨긴다.

## 신청 관리
신청 완료, 검토 중, 참가 가능, 참가 불가, 취소됨 상태로 운영한다. 서버에서 변경 권한을 확인하고 상태 변경을 감사 로그에 기록한다. 상태 수정은 회원의 마이페이지에 반영된다. 자동 이메일·문자 발송과 결제 연동은 추가 구축 범위다.

## 홈, About, 공지사항
콘텐츠 모델에 유형, 제목, 본문, 원고 상태, 수정 시각을 둔다. 이번 단계에서는 운영 원고 저장까지 제공한다. 기존 홈과 About을 교체하거나 공지사항을 공개하는 화면은 다음 단계에서 연결한다. 원고 확정과 사이트 공개를 혼동하지 않도록 표시한다.

## 권한과 운영 품질
회원은 본인의 신청만 읽는다. 운영자는 서버의 이메일 허용 목록으로 정한다. 브라우저 저장소에 관리자 권한이나 로그인 상태를 만들어 넣지 않는다. 운영 미리보기는 실제 개인정보를 포함하지 않으며 저장할 수 없다.

# 05 / 기술 기반과 데이터
## 현재 저장소의 기반
기존 React, Vinext와 Cloudflare Workers 구성을 유지하고 Cloudflare D1을 연결한다. 프로그램, 콘텐츠, 회원, 세션, OAuth 흐름, 신청, 감사 로그의 일곱 테이블을 사용한다. Drizzle 스키마와 SQL 마이그레이션을 함께 관리한다.

## 구글 로그인
Google의 authorization code 흐름과 PKCE, 일회성 state 검증을 사용한다. 서버가 토큰을 교환하고 Google UserInfo에서 확인된 이메일과 계정 식별자를 받는다. 앱 세션은 불투명 난수이며 데이터베이스에는 해시만 저장한다. 세션 쿠키는 HttpOnly와 SameSite를 사용하고 HTTPS에서 Secure를 적용한다.

## 쓰기 요청 보호
회원과 운영자 권한을 서버에서 검사한다. 쓰기 요청의 Origin을 검증하고, 프로그램 상태·가격·주소·입력 길이와 신청 동의를 확인한다. 회원과 프로그램의 조합에 유일성 제약을 두어 중복 접수를 방지한다.

## 배포 전제
기존 GitHub Pages 정적 배포만으로 로그인, 데이터베이스, 운영 API를 실행할 수 없다. 공개 전 Worker 서버 호스팅으로 전환하거나 동일 출처로 요청을 연결해야 한다. 운영 사이트와 QA 데이터베이스를 분리하고 Google 리디렉션 주소를 각각 등록해야 한다.

# 06 / 기업으로 성장하기 위한 운영 방향
## 제안하는 운영 순서
첫 단계는 실제 프로그램의 신청, 검토, 참가 안내를 안정화하는 것이다. 다음으로 반복 운영할 수 있는 기수와 멘토 프로세스를 정리한다. 이후에만 검증된 수요에 따라 클래스, 모임, 콘텐츠와 커뮤니티로 넓힌다.

## 측정할 질문
방문자가 어떤 프로그램을 보고 상세로 이동하는가? 로그인 이후 신청을 완료하는가? 신청부터 검토까지 얼마나 걸리는가? 참가자가 실제로 개선한 결과를 얻는가? 재참여 의사가 있는가? 현재 분석 데이터가 없으므로 수치 목표를 임의로 정하지 않는다.

## 수익과 운영의 균형
참가비 수입뿐 아니라 멘토 준비·리뷰 시간, 공간, 고객 응대, 취소 비용을 기수별로 기록한다. 정원을 늘리기 전에 피드백의 질과 운영 시간이 유지되는지 확인한다. 확장은 수요와 제공 역량을 함께 검증한 후 결정한다.

## 제안 로드맵
1단계: 실제 Google 로그인 연결, QA 데이터와 운영자 계정, 신청 운영 검증. 2단계: 홈·About·공지사항 공개 화면과 콘텐츠 발행 흐름. 3단계: 결제·알림·수강 이력 및 프로그램별 성과 측정. 일정은 운영 자원과 우선순위 확인 후 확정한다.

# 07 / 출시 조건과 문서 관리
## 현재 구현과 남은 설정
프로그램 목록과 상세, 반응형 스타일, 운영 콘솔, 실제 OAuth 코드, 회원별 신청과 상태 관리, 데이터 마이그레이션을 구현했다. QA 주소는 qa.offset.quest로 연결했다. Google Client ID와 Client Secret, 운영자 이메일 설정이 필요하다. 실제 구글 계정 로그인은 연결 정보 없이 완료할 수 없다.

## 운영 전 확인
실제 모집 상태와 일정, 공개 가격, 개인정보 안내와 보관 기준, 결제·환불 안내를 운영자가 확정한다. 이번 신청 폼의 1년 보관 기준은 초기 제안이며 실제 운영 정책에 맞게 조정해야 한다. 이를 법적 적합성 검토가 완료된 약관으로 취급하지 않는다.

## 출시 검증
독립된 로컬 데이터베이스로 권한, 초안 비공개, 수정 반영, 입력 검증, 중복·마감 신청, 회원별 조회, 상태 변경, 로그아웃을 검증한다. 실제 Google 왕복 로그인, 최종 공개 호스팅, 실제 기기의 시각·키보드 QA는 연결 이후에 수행한다. 운영 사이트를 변경하거나 배포 완료로 간주하지 않는다.

## 지속적으로 관리할 문서
루트 design.md: 디자인 규칙과 변경 기록. documentation/service-strategy.md: 서비스 해석과 범위. documentation/operations.md: 실행, 권한, 배포, 운영 절차. documentation/decisions.md: 결정과 미결 항목. 이 PDF는 service-strategy.md에서 재생성한다.
